## 一、实时通信技术候选方案全方位对比

在现代 Web 与移动端应用中，实现服务端向客户端实时推达数据的主流技术有三种：

| 评估维度 | WebSocket | Server-Sent Events (SSE) | HTTP Polling (短轮询/长轮询) |
| :--- | :--- | :--- | :--- |
| **通信协议** | 基于 TCP 的独立双向协议（`ws://`, `wss://`） | 基于标准 HTTP/1.1 或 HTTP/2 的单向流 | 标准 HTTP 请求-响应模式 |
| **双向能力** | **全双工**（客户端与服务端可随时互发） | **单向**（服务端推客户端；客户端发信走 HTTP） | 半双工（客户端拉取） |
| **连接成本** | 长连接常驻，占用系统文件句柄与内存 | 长连接常驻，遵循标准 HTTP 管道 | 短连接频繁握手，TCP 消耗极大 |
| **移动端友好性** | 弱网断线较多，需手动维护心跳重连 | 原生支持自动重连（`EventSource`） | 耗电、耗流量、延迟极高 |
| **鉴权与网关兼容**| 握手阶段需特殊处理，部分传统网关受限 | 完全复用现有 HTTP 鉴权与中间件 | 完全兼容现有架构 |
| **复杂度** | 高（需维护连接池、心跳、广播集群） | 中（仅需维护单向下发通道） | 低（逻辑简单，但服务端压力大） |

## 二、CampusTrade 业务规模与场景特征深度评估

### 1. 校园级业务特征分析
- **用户体量**：定位于单校及跨校二手交易，日活跃用户（DAU）在数千至数万量级，同时在线峰值连接数通常在数百至千级，**绝非千万级长连接互娱直播或大型社交场景**；
- **会话频次**：沟通多为“低频、脉冲式”（买家看中某件二手商品后，连续发 3~5 句询问成色、砍价并敲定面交地点，交易达成后沟通基本停止）；
- **可靠性要求压倒一切**：二手交易沟通涉及议价承诺与线下交付时间地点，**消息绝不能在弱网或网络切换时丢失**。

### 2. 常见架构误区：盲目采用“纯 WebSocket 全双工通道”发送消息
许多系统初期将消息的“发送”与“接收”全部强行塞入 WebSocket 私有协议帧中（即客户端通过 WS 发送 JSON，服务端在 WS OnMessage 中解析入库）。
在二手交易工程实践中，这种做法存在严重弊端：
1. **脱离成熟 HTTP 基础设施**：无法利用 Spring Security 的成熟过滤器链（`JwtAuthenticationFilter`）、无法享受 Spring MVC 的 `@Valid` 声明式参数校验、全局异常处理器 `GlobalExceptionHandler` 无法直接生效；
2. **本地事务与连接线程耦合**：WebSocket 连接线程容易被数据库写入阻塞，影响同一连接上的心跳响应；
3. **断线丢失风险极高**：当客户端按下发送按钮的瞬间若恰好网络抖动断开，WS 发送失败难以界定是“未发出”还是“未落盘”，导致客户端状态极其复杂。

## 三、CampusTrade 推荐核心架构：半双工解耦模式

为了兼顾开发效率、维护性与金融级交易可靠性，平台确立**“HTTP RESTful 上行写入 + WebSocket/SSE 下行实时通知”**的半双工解耦架构：

```text
       [ 发送消息 (上行) ] 
客户端 ──────────────────────────► HTTP POST /api/chat/messages
                                          │
                                          ▼
                                   [ 业务鉴权与校验 ]
                                   [ 事务写入 PostgreSQL (Source of Truth) ]
                                          │
                                          ▼ 
                                   [ 返回 200 OK 给发送方 ]
                                          │
                                          │ (异步事件驱动)
                                          ▼
                               [ WebSocket / SSE 推送管道 ]
                                          │
                                          ▼ (下行通知)
接收方 ◄────────────────────────── [ 推送新消息帧 / 未读红点 ]
```

### 1. 核心设计优势
1. **上行坚如磐石（RESTful 写入）**：
   - 消息发送调用 `POST /api/chat/messages`，完全复用现有 JWT 认证、用户冻结拦截、参数校验、敏感词过滤与 PostgreSQL 本地事务；
   - 接口返回即代表消息在数据库绝对安全落盘（`SENT` 状态），客户端立即获知明确结果并更新本地 UI，弱网下支持标准的 HTTP 重试；
2. **下行极速轻量（实时推送）**：
   - 当消息成功落盘后，通过下行实时通道（WebSocket STOMP 或 SSE）将轻量级通知帧推送到接收方的在线终端；
   - 接收方若正处于当前会话窗口，直接无缝追加气泡；若在其他界面，更新全局未读角标；
3. **天然平滑降级（Fail-Over）**：
   - 若实时推送服务发生抖动或用户暂时离线，**业务完全不受影响**！用户下次打开 App 或切换页面时，通过标准 REST 游标拉取即可完整获取所有离线消息。

## 四、连接管理、保活与去重机制设计

若未来采用 WebSocket 作为下行通知载体，需严格遵循以下连接规范：

### 1. 连接建立与握手鉴权
- **端点规划**：`/ws/chat`；
- **鉴权方式**：由于标准浏览器与移动端 WebSocket API 在握手阶段无法自定义 HTTP Header，采用 URL Query 传参方式携带 JWT：
  `wss://api.campustrade.com/ws/chat?token=eyJhbGci...`
- **握手拦截器（`HandshakeInterceptor`）**：
  1. 解析 Token 并验证有效性；
  2. 提取 `username` 并查询用户状态，若 `status == 'FROZEN'` 坚决拒绝握手；
  3. 将验证通过的 `userId` 写入 WebSocket Session 的 Attributes 中，供后续路由使用。

### 2. 双向心跳与死连接剔除（Heartbeat）
- **心跳周期**：客户端每 **30 秒** 发送一次轻量级 `PING` 帧；
- **服务端响应**：服务端收到后立即返回 `PONG` 帧；
- **超时淘汰**：若服务端超过 **90 秒** 未收到某连接的心跳，判定该连接已断网或崩溃，主动关闭 Session 并从在线管理池中注销，释放服务器资源。

### 3. 断线重连与消息增量同步机制
- **客户端策略**：网络异常断开后，客户端启动指数退避重连（1s, 2s, 4s, 8s... 最大 30s）；
- **离线补齐（Sync）**：重连成功后，客户端主动调用增量拉取接口：
  `GET /api/chat/messages/sync?sinceMessageId={localMaxId}`
  拉取离线期间由数据库已持久化的所有新消息，确保一条不漏。

### 4. 幂等去重防重复（Duplicate Elimination）
- 客户端在发送消息前本地生成 `clientMsgId`（UUID v4）；
- 服务端数据库依靠 `uk_msg_client_id (sender_id, client_msg_id)` 唯一索引进行兜底拦截；
- 无论网络超时重发多少次，数据库物理级拦截并发冲突，保证会话中绝对不出现重复气泡。
