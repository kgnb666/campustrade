## 一、领域模型概览

在 DDD（领域驱动设计）指导下，校园二手交易即时通讯不属于泛社交网络，而是**围绕交易生命周期的协作沟通子域**。
其核心由两大实体构成：
1. **`Conversation`（会话聚合根）**：负责维护沟通双方的参与关系、关联的商品/订单上下文、会话的全局状态、双方独立的未读计数以及最新消息快照；
2. **`Message`（消息明细实体）**：表示会话中产生的具体单向通信内容，包含发送者、接收者、消息类型、消息体内容、状态及已读时间戳。

```text
+-------------------------------------------------------------+
|                     Conversation (聚合根)                   |
| - id: Long                                                  |
| - userAId: Long, userBId: Long                              |
| - goodsId: Long, orderId: Long                              |
| - lastMessageId, lastMessageContent, lastMessageTime        |
| - unreadCountA: Integer, unreadCountB: Integer              |
| - status: ACTIVE | BLOCKED | CLOSED                         |
+-------------------------------------------------------------+
                              | 1
                              |
                              | N
+-------------------------------------------------------------+
|                       Message (实体)                        |
| - id: Long                                                  |
| - conversationId: Long                                      |
| - senderId: Long, receiverId: Long                          |
| - msgType: TEXT | IMAGE | SYSTEM                            |
| - content: Text                                             |
| - extraData: Json                                           |
| - isRead: Boolean, readTime: LocalDateTime                  |
| - status: NORMAL | RECALLED | SHIELDED                      |
| - clientMsgId: String (UUID)                                |
+-------------------------------------------------------------+
```

## 二、一对一聊天模型架构选型对比

在即时通讯数据建模中，业界常见两种模式：

### 方案 A：`Conversation`（会话表） + `Message`（消息表）双层结构
- **结构说明**：会话作为独立的数据表存储，包含参与者 `userAId`, `userBId`、关联 `goodsId`、最新消息快照和双方未读数；每条消息外键关联 `conversationId`。
- **优点**：
  1. **会话列表查询极速**：查询“我的会话列表”只需单表分页 `WHERE userAId = ? OR userBId = ? ORDER BY lastMessageTime DESC`，索引命中率 100%，耗时固定在 1~2ms；
  2. **聚合业务状态天然收口**：会话级业务字段（商品关联、订单绑定、双方屏蔽关系、各自未读消息计数）有明确挂载实体，无需在消息表中冗余；
  3. **未读数维护原子可控**：在会话行上直接进行 CAS 或原子自增自减，避免每次打开应用执行高成本的 `COUNT(is_read=false)` 聚合扫表；
  4. **扩展性极佳**：便于未来无缝扩展系统安全提示、会话置顶、会话标签等功能。
- **缺点**：新增会话或发送新消息时，需要同时维护消息表插入与会话表快照更新。

### 方案 B：纯 `Message`（单表扁平结构）
- **结构说明**：不设会话表，所有消息只记录 `senderId`、`receiverId`、`content`、`createdTime`；会话列表通过 SQL 动态计算。
- **缺点与硬伤**：
  1. **查询性能灾难**：查询“我的聊天列表”需要对全表做 `GROUP BY LEAST(senderId, receiverId), GREATEST(senderId, receiverId)` 配合窗口函数提取最新一条消息。当单表消息量达到数十万条时，查询产生严重的临时表（Temporary Table）与文件排序（Filesort），数据库 CPU 飙升；
  2. **会话上下文无处安放**：同一对买卖双方可能针对不同商品进行沟通，单表难以清晰维护会话状态（如针对商品 A 咨询已结束，但买家又就商品 B 咨询）；
  3. **未读数计算代价不可承受**：每次拉取会话列表必须对该用户的所有未读消息进行聚合统计。

### 架构决策
$$\mathbf{决策结果：坚决采用方案\ A（Conversation + Message\ 双层模型）}$$
方案 A 完美契合 CampusTrade 的高一致性与高维护性原则，在单机 PostgreSQL 下即可提供千万级消息承载能力且查询性能极度稳定。

## 三、会话（Conversation）生命周期状态机

二手交易聊天不同于熟人社交，具有极强的**生命周期时效性**。

### 1. 会话状态定义

```text
     [买家发起咨询]
           │
           ▼
      ┌──────────┐      用户主动拉黑 / 违规屏蔽
      │  ACTIVE  │ ────────────────────────────► ┌──────────┐
      └──────────┘                               │ BLOCKED  │
           │                                     └──────────┘
           │ 交易终态+超时 (自动)                       ▲
           │ 或双方手动关闭 (主动)                      │
           ▼                                            │
      ┌──────────┐      违规屏蔽                        │
      │  CLOSED  │ ─────────────────────────────────────┘
      └──────────┘
```

1. **`ACTIVE`（正常交流态）**：
   - 初始状态；双方均可正常发送文字、图片与查看历史消息；
   - 支持系统交易事件卡片的实时推入。
2. **`BLOCKED`（已拉黑/屏蔽态）**：
   - **触发场景 1（用户主动）**：买卖某一方遭受骚扰，点击“屏蔽此人”，状态转为 `BLOCKED`；
   - **触发场景 2（平台治理）**：管理员介入，认定该会话存在诈骗或恶性违规，直接封禁会话；
   - **行为表现**：被屏蔽方尝试发信时，系统提示“消息已发送但被对方拒收”或“会话已冻结，无法发送”。
3. **`CLOSED`（已关闭/归档态）**：
   - **触发场景 1（自动超时归档）**：关联订单进入 `COMPLETED` 超过 7 天，或关联商品被标记为 `SOLD_OUT` / `OFF_SHELF` 且无未完成订单超过 3 天，系统自动归档；
   - **触发场景 2（手动归档）**：双方达成一致结束咨询；
   - **行为表现**：只读模式，双方可翻阅历史聊天记录，但输入框禁用，不可再追加发送新消息。

## 四、消息（Message）生命周期与撤回机制深度论证

### 1. 消息状态机流转

```text
[客户端发送] ──► SENDING (前端临时态)
                      │
                      ▼
               入库成功 ──► SENT (服务端落盘，状态 NORMAL)
                               │
                               ├──────────────────────┐
                               ▼                      ▼
                        接收方打开会话          发件人 2 分钟内撤回
                               │                      │
                               ▼                      ▼
                             READ                  RECALLED
                         (is_read=true)        (content保留，状态变更)
                               │
                               ▼ 管理员判定违规
                            SHIELDED
                         (内容屏蔽展示)
```

### 2. 核心争鸣：二手交易场景下是否允许消息撤回？
在传统社交 IM（如微信）中，允许 2 分钟内撤回消息以规避错别字尴尬；但在**交易履约与纠纷仲裁**场景下，随意撤回存在巨大黑灰产风险：
- **风险场景**：卖家在聊天中承诺“保修半年”或“绝对正品无暗病”，买家付款下单后，卖家立刻撤回承诺，事后发生纠纷时买家无法自证；
- **平台仲裁原则**：平台治理中心（Stage 6-B）在处理买家与卖家纠纷时，必须以客观原始证据为依归。

### 3. 架构撤回规范确立
1. **严格时间窗口限制**：仅允许发信人在**发送成功后 2 分钟内**发起撤回；超过 2 分钟禁止撤回。
2. **绝对物理保留（软撤回）**：
   - 撤回操作**绝不执行数据库 `DELETE` 操作**！
   - 数据库将该消息 `status` 字段变更为 `'RECALLED'`；
   - 客户端正常渲染为：“你撤回了一条消息” / “对方撤回了一条消息”；
   - **管理员治理审计端不受撤回影响**：后台管理员在处理争议工单时，可直接查看被撤回消息的原始内容快照（标注【用户已于 xx 时间撤回】），彻底杜绝销毁交易承诺欺诈行为。
3. **系统卡片与关键状态不可撤回**：所有 `SYSTEM` 类型的消息（如订单状态变动、地点确认卡片）由系统生成，任何用户无权撤回。

## 五、消息类型设计与边界收口

### 1. 允许的消息类型 (`msg_type`)

| 消息类型 | 代码标识 | 承载内容与约束 | 业务意义 |
| :--- | :--- | :--- | :--- |
| **纯文本** | `TEXT` | `content` 存 UTF-8 字符串；长度限制 **1~1000 字符**；前置敏感词过滤。 | 商品咨询、砍价、面交细节约定。 |
| **实物图片** | `IMAGE` | `content` 存 MinIO 图片绝对 URL；限制格式 `jpg`, `jpeg`, `png`, `webp`；文件体积 **<= 5MB**。 | 实物成色验货、瑕疵局部特写、小票凭证展示。 |
| **系统事件卡片** | `SYSTEM` | `content` 存标题；`extra_data` 存结构化 JSON（包含 `event_type`, `order_id`, `goods_id`, `action_url`）。 | 订单状态变更（下单/接单/完成）、平台防诈安全预警。 |

### 2. 明确拒绝与延期的消息类型

1. **❌ 坚决延期：任意文件传输（PDF, Word, ZIP, RAR, APK 等）**：
   - 拒绝理由：校园网环境下易沦为病毒木马传播载体；且大文件传输对服务器带宽和 MinIO 对象存储形成巨大压力。二手交易无需收发代码包或文档。
2. **❌ 坚决延期：语音消息（Audio）与语音通话**：
   - 拒绝理由：涉及音频转码、分片传输、STT（语音转文字审核）以及信令协商，研发成本极高，违背精简闭环原则。
3. **❌ 坚决延期：视频聊天（Video Call）**：
   - 拒绝理由：需要架设 WebRTC SFU/MCU 媒体网关，与校园二手面交场景定位严重脱节。
