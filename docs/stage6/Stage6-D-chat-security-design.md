## 一、IDOR（水平越权访问）深度防御体系

在即时通讯系统中，聊天记录高度私密，IDOR 是最致命的漏洞形态（例如恶意用户通过穷举 `conversationId` 获取他人的私密聊天内容或向他人的会话冒名发信）。

### 1. 强制权限校验范式（Zero-Trust 契约）
在任何涉及会话与消息的 API 处理层（拉取历史消息、标记已读、撤回消息、拉黑会话）：
1. **服务端必须主动鉴权**：
   - 首先通过主键查出 `Conversation` 实体；若会话不存在，返回 `404 Not Found`；
   - 严格比对：
     ```java
     Long currentUserId = SecurityUtils.getCurrentUserId();
     if (!conversation.getUserAId().equals(currentUserId) && !conversation.getUserBId().equals(currentUserId)) {
         log.warn("检测到越权访问聊天会话: currentUserId={}, convId={}, a={}, b={}", 
                 currentUserId, conversation.getId(), conversation.getUserAId(), conversation.getUserBId());
         throw new BusinessException(ResultCode.FORBIDDEN.getCode(), "无权访问此聊天会话");
     }
     ```
   - 绝不依赖客户端传入任何 `userId` 参数判定归属。
2. **发件人身份伪造防御**：
   - `Message` 实体入库时，其 `sender_id` **强制直接取自当前已通过 Spring Security 认证的 `SecurityContext`**，客户端传入的任何身份标识一律作废；
   - 接收方 `receiver_id` 由服务端根据会话的 `userAId` 与 `userBId` 自动推导（当前用户为 A 则接收方为 B，反之亦然），杜绝在 A 与 B 的会话中把消息发送给第三方 C 的篡改行为。

## 二、聊天发起准入权限机制权衡与推荐方案

针对“谁有权限发起即时沟通”，对比三种架构方案：

### 1. 方案对比与评估

| 方案模式 | 准入规则 | 优势 | 缺陷与安全风险 | 评估结论 |
| :--- | :--- | :--- | :--- | :---: |
| **方案 A：泛社交全开放** | 任意注册用户可向全站任意用户自由发起聊天 | 社交灵活性最高 | 垃圾广告、群发骚扰、校外引流与杀猪盘泛滥，监管成本极高。 | **❌ 坚决否决** |
| **方案 C：强订单绑定** | 只有已经下单（`trade_order`）的用户才能沟通 | 范围极度收敛，防骚扰能力极强 | **严重违背二手交易现实逻辑**：买家无法在下单前咨询成色、议价或确认是否有现货。 | **❌ 过于严苛** |
| **方案 B：商品锚点准入（推荐）** | **必须针对某件在售商品发起会话**，以交易标的为准入纽带 | 满足咨询议价刚需，杜绝无标的骚扰，业务场景高度闭环。 | 需要防止对同一卖家恶意反复发起商品咨询。 | **✅ 强烈推荐** |

### 2. 推荐准入综合规则（方案 B + 信用防御 + 状态隔离）
买家向卖家发起新会话时，必须同时满足以下 **6 重物理门槛**：
1. **标的存在性与有效性**：必须传入合法的 `goodsId`，且目标商品必须处于 `ON_SALE`（在售）状态；
2. **自聊防御**：商品卖家不能是当前登录用户（`goods.sellerId != currentUserId`），禁止自导自演；
3. **用户可用性检查**：发起方与目标卖家的 `user.status` 必须均为 `ACTIVE`；若任一方处于 `FROZEN`，直接拒绝；
4. **信用门槛防护**：发起方信用分等级若处于 **`TERRIBLE`（信用严重违规）**，禁止发起任何新会话，提示“您的信用分极低，已被限制发起聊天”；
5. **黑名单防护**：若卖家已将买家加入会话黑名单（`BLOCKED`），禁止发起；
6. **防刷单限流**：同一买家 1 分钟内最多向不同卖家发起 3 个新会话，防止自动化脚本批量扫号咨询。

## 三、用户隐私保护与外部联系方式防诈风险控制

在校园二手交易中，黑灰产或诈骗分子最典型的欺诈手法是：**“引导脱离平台转微信、QQ 或扫描二维码付定金，随后拉黑跑路”**。

### 1. 处理策略：智能风控提示，而非粗暴阻断
- **过度阻断的弊端**：完全屏蔽手机号或微信号，会导致正常学生在约定面交时无法互留电话，产生极差的用户体验，迫使用户使用隐晦错别字（如“V我”、“薇信”）；
- **智能化柔性风控方案**：
  1. **敏感通信特征实时正则匹配**：
     - 中国大陆手机号正则：`(?:\+?86)?1[3-9]\d{9}`；
     - 常见社交软件引流特征词：`微信`、`微信号`、`wx`、`v信`、`QQ`、`转账`、`定金`、`支付宝`、`二维码`；
  2. **系统即时下发安全防诈卡片（System Safety Notice）**：
     - 当检测到某条消息命中上述规则时，该消息正常投递，但系统**自动在该消息下方推入一条显目的高亮安全警示卡片**：
       > ⚠️ **【校园反诈安全警示】**  
       > 对方在聊天中提及了外部联系方式或资金转账。平台郑重提醒：**校园二手交易请务必坚持“同校面交、当面验货、验货后当面付款”**。凡是要求提前支付定金、运费或点击外部链接的，均属于高危诈骗！

### 2. 图片内容安全控制
- 聊天中上传的实物图片，必须复用平台 MinIO 鉴权白名单；
- 限制图片仅支持常见光栅格式（`jpg`, `png`, `webp`），严格过滤 SVG 等易携带 XSS 攻击载荷的矢量格式；
- 前端限制单个图片展示尺寸，禁止在聊天界面执行任何不受信的 HTML 渲染。

## 四、基础风控与恶意骚扰反制机制

1. **高频发送限流（Rate Limiting）**：
   - 依托 Redis 滑动窗口或令牌桶：
     - 单用户发送消息频率上限：**2 条 / 秒**；
     - 超出限制直接拦截并返回 `429 Too Many Requests`（“发送过于频繁，请稍候”）；
2. **文本内容敏感词过滤（Trie 树字典过滤）**：
   - 建立内存敏感词 Trie 树，覆盖：政治反动、涉黄涉赌、暴恐枪支、毒品违禁品；
   - 命中高危敏感词的消息直接阻断，返回 `400 Bad Request`（“消息内容包含违规敏感词，已被平台拦截”），并在系统日志中记录潜在风险账号；
3. **用户端主动防御：一键拉黑（Block User）**：
   - 会话右上角提供“屏蔽此用户”按钮；
   - 触发后，将当前会话状态置为 `BLOCKED`，拦截被拉黑方后续的所有消息投递；
4. **与 Stage 6-B 举报治理无缝衔接**：
   - 聊天界面每一条消息均支持长按举报；
   - 一旦管理员查实恶意言论、性骚扰或诈骗，立即对加害方执行账号冻结（`FREEZE_USER`）并扣减信用分，实现全站治理联动。
